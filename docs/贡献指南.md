# 贡献指南

## 先跑测试

改动之前先确认基线是全绿的：

```
node edge-bridge/tools/test-bridge.mjs
node edge-bridge/tools/test-plugin.mjs
node edge-bridge/tools/test-server.mjs
node edge-bridge/tools/test-capture.mjs
node edge-bridge/tools/test-contract.mjs
node edge-bridge/tools/test-page-in-edge.mjs
```

共 318 项断言。前五套不需要浏览器；`test-page-in-edge` 需要 Edge 116+，起不来会打印 `SKIP` 并退出 0。

本机没有 `node` 时用 DSH 自带运行时（Electron）：

```
export ELECTRON_RUN_AS_NODE=1
"D:/DeepSeek Harness/DSH NEXT/DSH NEXT.exe" edge-bridge/tools/test-bridge.mjs
```

## 目录规矩

| 位置 | 放什么 |
| --- | --- |
| `plugin/index.js` | 只做装配：令牌、监听、控制器、抓取引擎、dispose |
| `plugin/lib/` | 单一职责模块；`ws.js` 不 import 其它模块，`bridge.js` 不 import `tools.js` |
| `plugin/lib/tools.js` | 工具定义 + 文本渲染；不做 DOM 操作、不发网络请求 |
| `extension/page.js` | 只放注入页面的自包含函数。**不能**引用外部变量，只能用一个 `options` 参数和页面全局 |
| `extension/background.js` | 拨号、重连、方法分发。`HANDLERS` 的键就是对外方法名 |
| `tools/` | 测试、fixture、运维脚本。测试之间不共享状态 |

## 改动的三条硬规矩

### 1. 加 method 必须两侧同步

新增一个浏览器方法要动四个地方：

1. `extension/background.js` 的 `HANDLERS`（实现）。
2. `plugin/lib/bridge.js` 的 `HOST_CAPS`（声明）。
3. `plugin/lib/tools.js`（如果要对模型暴露）。
4. `tools/test-contract.mjs` 的期望值（如果要断言）。

`HOST_CAPS` 与 `HANDLERS` 的集合必须完全相同，`test-contract` 会拦住不同步的提交。

### 2. `page.js` 的函数必须自包含

这三个函数 (`readPage` / `actPage` / `inspectPage`) 是通过 `Function.prototype.toString()` 序列化后注入页面的。这意味着：

- 不能引用闭包外的任何变量或模块。
- 辅助函数必须定义在函数体内，或者作为兄弟函数一起注入。
- 不能用 `import`。
- 测试会用同样的方式注入（`(${readPage.toString()})(options)`），所以本地改完能立刻验证。

### 3. 每个工具输出文本，不输出 JSON

`output.render` 的约定是把结构化结果压成一段人类/模型都能直接读的文本。不要返回 JSON 树让模型自己走——这是这个插件的核心设计，测试里也有对应断言。

## 提交前检查

```
# 语法
node --check edge-bridge/plugin/lib/tools.js
node --check edge-bridge/extension/page.js
node --check edge-bridge/extension/background.js

# 契约
node edge-bridge/tools/test-contract.mjs
```

如果是改扩展，**记得在 `edge://extensions` 点重新加载**再手动验证；只重启 DSH 不会替换 service worker 的代码。这是这个项目最常见的一次性错误。

## 文档同步

改了工具数量、参数、能力位或版本号时，同步这几处（`test-contract` 会检查前两处）：

- `README.md` 与 `README.en.md` 的工具表、自测项数。
- `docs/使用指南.md` 与 `docs/usage.md` 的参数表。
- `docs/CHANGELOG.md` 记一条。
- `docs/内部架构.md` / `docs/internal-architecture.md`（如果是架构性改动）。

## 测试写法

用 `check(name, condition, detail)` 累积结果，不要用 `assert` 抛异常——一次跑完所有断言比停在第一个失败更有用：

```js
check('edge_act reports the ref it used', /clicked ref e1/.test(text), text);
```

名字写成"期望的行为"，而不是"测试 X 函数"。失败时 `detail` 会打印出来，所以把关键文本传进去。

## 提 PR

描述里写清三件事：

1. **修的是什么失败**（不是"加了什么功能"）。
2. **怎么复现**（哪一步、什么回执）。
3. **哪条断言能证明它修好了**。

如果一个改动无法用现有六套测试表达，说明它可能需要先补一层测试设施——那本身也是可以单独提的 PR。
